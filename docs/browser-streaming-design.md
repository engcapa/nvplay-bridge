# Browser 模式向 Claude Code 实时转发 SSE 的设计

日期：2026-11-08。状态：核心方案已实现并通过测试，结果见 [流式回归记录](streaming-regression-report.md)。

## 目标与现场依据

Claude Code 设置 `stream=true` 时，上游产生 thinking、正文或工具参数后，桥接应在正常负载下约 500ms 内向客户端交付对应增量，不再等整轮推理完成。这个时间是桥内转发目标，不包含模型首 token 的等待时间，也不保证 CC 界面如何展示 thinking。

本次手工测试确认了三个问题：

- Playground 已经持续返回 HTTP 200/SSE，但 `BrowserUpstream.generate()` 只在流结束时返回完整字符串，CC 在此期间只能收到 `message_start` 和 ping。
- 一轮 `max` 推理在约 602 秒触发桥接超时，随后收到了 CC 的重试；超时前浏览器已经收到了大量 reasoning 数据。
- CC 停止后，检查时仍有两个页面响应流未结束：原超时请求和后来的重试。现有超时/断开路径没有可靠地终止浏览器 fetch。

现有 `stream_anthropic()` 已能逐项发送 thinking/text，但工具参数仍在结束后统一输出，因此浏览器读取和工具转换两层都需要改造。

## 推荐结构

保留页面签发请求令牌和替换 fetch 请求体的方式。第一版继续通过 CDP 轮询，改成每次取走新增数据；无需引入 Playwright、浏览器扩展或 WebSocket 服务。

数据按以下步骤流动：

1. 页面 fetch 的克隆 reader 用流式 TextDecoder 解码，写入本次请求专属的待取队列。
2. 一个工作线程独占对应标签页的 CDP 连接，每约 100ms 原子取走一批新增数据及状态。
3. 工作线程解析完整 SSE 事件，沿用 `_chunk_events()` 转成 thinking/text/tool/usage/finish/error。
4. 通过有容量限制的异步队列交给 FastAPI；事件循环收到后立即生成 Anthropic SSE。
5. `stream=false` 从同一事件源收集最终 JSON，保持非流式接口可用。

实现接口如下：

```python
BrowserUpstream.stream(body, timeout=3600, cancel=None, trace=None) -> Iterator[str]
BrowserPool.stream(body, timeout=3600, cancel=None, trace=None) -> Iterator[str]
iter_events(payload, headers, *, buffered=True) -> AsyncIterator[dict]
```

浏览器适配层检查响应状态、处理 EOF/错误，向工作线程交付已解码的 SSE 片段；失败通过异常表示。线程到事件循环的队列传输归一化后的事件，控制错误独立于有界数据队列，避免队列满时无法结束。CDP 的所有收发都留在同一工作线程。`generate()` 通过连接流片段保留原有接口，方便已有脚本迁移。

## 页面请求与增量读取

每次请求分配独立 `request_id` 和状态对象，保存 status、content-type、待取数据、完成标记、错误、AbortController 和 reader。

- fetch 拦截命中后立即消费已装填的 body，避免同一 body 被页面后续请求再次使用。
- reader 回调捕获本次状态对象；旧请求的晚到回调不能写入下一次请求的状态。
- `drain(request_id)` 在一次同步 JS 调用中取数据并移除已取部分，同时返回状态。完成标记出现时，也必须先交付最后一批数据再处理 EOF。
- 仅传新增数据，避免反复经 CDP 复制累计全文。工作线程保留未完成 SSE 帧，不保留已处理的整轮响应。
- 明确处理非 200、网络错误、页面重载、CDP 断开和 `status=200` 但 reader 出错的情况。后者不能继续当作成功回答。
- 使用带版本号的补丁。升级时应在空闲标签页重载后安装，不能依赖现有 `__bridgeInstalled=true`，也不能反复套 fetch 包装。

初始容量建议：单次 drain 约 64KiB，页面待取队列 4MiB，Python 事件队列总量约 1MiB，并限制单项大小。容量按编码后字节统计，切片不得破坏 Unicode 字符。消费者变慢时施加背压，等待必须可取消；超过限定时间仍不能交付则中止本次请求，禁止丢片段后继续拼答案。

页面原本的 UI 仍会消费原响应，页面自身 DOM/内存增长不由桥接队列完全控制，继续保留标签页刷新阈值。

SSE 解析器必须跨 drain 保存半帧，处理 CRLF、空行事件边界、多行 data、注释、usage 尾帧和 `[DONE]`。JSON 或事件可能任意分片，禁止对每次 drain 单独 `splitlines()` 后忽略不完整内容。网络断开、截断 JSON、缺少有效结束状态不能伪装成正常 `message_stop`。

## Anthropic 输出与工具调用

thinking 增量映射为 `thinking_delta`，正文映射为 `text_delta`。正文/思考类型切换时关闭旧块，再开始新块。沿用当前 Kimi thinking 兼容表示，不伪造 Claude 的签名；通过真实 CC 验证接收行为。

工具输出需要把现有 `tool_buf` 改成有状态的内容块转换器：

- 按上游 `tool_calls[index]` 保存工具 ID、名称、参数片段及 Anthropic block index。
- 等 ID 和名称可确定后发送 `content_block_start(tool_use)`，随后逐批发送 `input_json_delta`，不等待参数 JSON 完整。
- ID/名称还未到齐时只暂存该工具的片段；结束仍缺必要元数据则报告协议错误，不临时编造另一个 ID 或工具名。
- 完整工具参数在完成时校验，不能在收到第一个参数片段时执行工具；工具执行仍由 CC 处理。
- 内容块索引连续递增、每块只 start/stop 一次，停止原因映射为现有 `tool_use` / `end_turn` / `max_tokens`。

第一版采用连续内容块输出：首个工具可实时发送参数；若上游交错发送多个工具，则暂存后续工具片段，等当前工具可确定结束后依序输出。若上游只有全局 finish 才能确定结束，就在该时点关闭当前块并输出其余工具。这样不会依赖 CC/SDK 对多个同时打开内容块的支持。缓冲同样受容量限制。

第一版对工具参数开始后又出现正文/思考的异常交错显式报告协议错误，避免产生无法表示的块顺序；不重开已结束的块。未来若要让多个并行工具都实时展示，需先验证目标 SDK 对交错 block 的支持，再独立扩展。

finish_reason 是模型结束信号，不能立即结束 HTTP 流：仍需读取尾部 usage，最后发送一次 `message_delta` 和 `message_stop`。累计 usage 取最后有效快照，不能把每帧累计值相加；首帧若已有输入 token 数，应填入 `message_start`。当前沿用 message_start 的 0 占位和尾部 message_delta 更新；真机 CC 测试确认最终输入/输出用量被正确接收（1933/43），不能把首帧占位值视为最终用量。

原有 HTTP 响应头 `text/event-stream`、`Cache-Control: no-cache` 和 `X-Accel-Buffering: no` 继续保留。ASGI 中不得再引入整轮聚合或压缩缓冲。

## 重试与已交付内容

定义 `committed`：第一条 thinking/text/tool 内容事件已经交给下游。从该时点起，无法保证客户端没有看到它，按不可撤回处理。message_start、ping 和纯 usage 不触发 committed。

| 情况 | stream=true 的处理 |
|---|---|
| 未提交内容，完全空响应 | 在剩余总时限内纠正重试一次 |
| 未提交内容，仅占位文本 | 暂扣占位，确认后纠正重试一次 |
| 已发出思考，最终正常 stop 但无正文/工具 | 报告无有效回答错误，不把第二轮答案拼进当前消息 |
| 已发出思考，输出预算耗尽 | 如实结束并返回 `max_tokens`，保留部分思考 |
| 内容交付后发生网络错误/超时 | 发送 SSE error 并结束，不发送成功结束事件，不透明重试 |
| 客户端取消 | 停止生成和清理，不重试 |

占位文本 `[Tool use interrupted]` 用有限前缀缓冲处理：只要当前正文仍可能是完整占位文本就暂扣；一旦匹配失败就释放全部暂扣正文。不能只检查单个 delta，否则会漏掉被拆开的占位文本。若已经发出思考，再遇到占位文本，也不能静默重做整轮。

`stream=false` 没有向客户端交付正文，可以保留当前 thinking-only/占位纠正重试，但两次尝试要使用独立的聚合状态，丢弃失败尝试的内容。`max_tokens=1` 的 CC 非流式模型探测继续走此路径。重试全程仍发送心跳，并在日志中分别记录尝试数和 token 消耗。

## 超时、取消与池归还

将超时分开记录：池排队、页面准备/发送、首个上游数据、流空闲、请求总时限。使用单调时钟；CDP 轮询成功和发给 CC 的 ping 都不能刷新上游空闲计时。

默认首个数据超时 120 秒、流空闲超时 90 秒；`BROWSER_TIMEOUT` 保留为总上限，按用户要求在默认值及启动配置中设为 3600 秒。重试共享本次请求的总预算，不能每次重新获得完整时限。真实流式本身不会取消硬时限，因此本次同时将旧的 600 秒限制改为一小时。

仓库内 CC 配置及全局配置辅助脚本已将 `API_TIMEOUT_MS` 从 600000 调为 3900000（65 分钟），为一小时请求留出余量。已运行的 CC 需要重启加载配置；用户现有全局配置不会被自动覆盖。心跳用于避免空闲断开，不能代替总时限配置。

取消流程：

1. StreamingResponse 被取消或检测到 request disconnect，设置线程安全的 cancel 标记。
2. 工作线程在排队、CDP 读取、等待背压和生成期间都检查该标记，以匹配 request_id 调用页面 AbortController，并停止 reader。
3. 等 fetch 终止确认，关闭本次内容状态并清理 body、残留数据和错误，再做计数/刷新判断。
4. 最后才归还标签页。若 abort/CDP 清理失败，隔离该标签页，重载或重建成功后再入池，不能把仍有旧流的页面交给下一条请求。

超时和异常复用同一清理流程。停止接收客户端数据后，原线程仍运行的问题不能靠 `asyncio.to_thread()` 取消自动解决；必须显式传递 cancel，并等待工作线程完成清理。清理有独立短时限，失败由池恢复逻辑接管。

一个标签页在整个流及清理期间只有一个所有者。现有 Pool 在生成后先 `_queue.put()`、再读页面文本和更新刷新状态的顺序需要调整，避免下一条请求已经借出标签页时，上一次请求仍操作其 CDP 连接。

首版仍每 10 秒无下游内容时发送 ping，覆盖排队、页面准备、首包等待和允许的重试。消费者取消后不再发送 ping。一次取消/错误只记一个终态，不能重复归还池槽。

## 验证与实施顺序

先建立可控制暂停的假上游：发第一段后阻塞，断言 HTTP 客户端已经收到对应 thinking/text/tool delta；随后再放行结束。仅在完整结果里搜索 SSE 字样无法证明实时转发。

必须覆盖：

- SSE 在每个字节边界切分、中文及 emoji、多行 data、CRLF、usage 尾帧和结束状态。
- 思考/正文顺序、工具参数分片、元数据晚到、两个工具交错、内容块索引及完整 JSON。
- 占位分片、空回复重试、首次思考交付后禁止重试、预算耗尽及中途断流。
- 排队和重试时心跳；持续有效数据不触发 idle timeout，总时限仍有效。
- 客户端在排队、思考、工具参数和队列满时断开；abort 得到执行，清理前不能复用标签页。
- 三标签并发无串流、旧回调不污染新请求、慢客户端下缓冲有界、清理失败后池恢复。
- 非流式响应及 OpenAI/NVCF 模式回归，现有转换/循环纠正行为不回退。

日志增加统一 request_id、attempt、tab_id，以及首上游数据/首下游内容时间、首正文时间、取消原因、abort 结果、池归还结果、缓冲峰值和 usage。不逐 token 写日志，定期记录进度摘要即可；耗时测量须证明源头有数据后，CC 网络连接在流结束前实际收到了内容。

实施顺序：先完成页面请求隔离、drain 和 abort；再接入工作线程、事件队列及取消；随后改工具内容块和重试规则；最后做三标签真机测试并更新启动配置与 README。第一批部署需安排在手工测试停止且无请求的时段，重载旧补丁页面后再启动新流式版本。
