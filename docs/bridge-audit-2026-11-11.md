## 修改、逻辑和影响

| 修改 | 实现逻辑 | 影响及预期结果 |
| --- | --- | --- |
| 保留 token 截断原因 | `_stop_reason` 优先处理上游 `length`，之后才根据工具存在映射 `tool_use` | 已完整收到工具参数但输出触顶时，也向 CC 返回 `max_tokens`，保留截断语义。参数本身不完整时仍显式报错。 |
| 非流式响应完整性校验 | JSON 聚合要求结束标记、工具 ID 与名称齐全；缺失返回 502 | 避免残缺响应被当作成功，或用 `unknown` 工具名、临时 ID 掩盖问题；客户端能按失败重试。流式响应已有相应校验。 |
| 请求关联和分阶段诊断 | Messages/Responses 返回 `request-id` 与 `x-request-id`，日志共享 `request_id`；新增 `browser_lease`、`browser_sent`、`messages_first_block`、`messages_done/failed`、`http_complete` | 能区分排队、页面准备、触发发送、上游等待、响应转换与 HTTP 交付；避免仅凭 `browser_done` 就认定客户端成功。 |
| 工具调用与工具结果诊断 | 记录工具参数的规范 JSON SHA-256；识别相同新旧字符串；从下一次 CC 请求记录最近工具结果的错误分类 | 后续可直接定位参数是否一致，以及失败属于模型输入、CC 工具执行还是桥接；不会自动更改工具参数。日志不记录源码或命令输出。 |
| 监控摘要补充 | `monitor_bridge.py --snapshot` 增加 `recent_client_errors`、`recent_tool_errors` | 转换失败和编辑失败可见，即使上游已经报告完成。 |

停止原因覆盖属于代码审查发现的缺陷，并非已确认的生产触发案例。
历史 4 次 `length` 都是 CC 请求和上游预算 32000、工具调用数为 0；
其中 3 次将 32000 个 completion tokens 全部用于思考。
