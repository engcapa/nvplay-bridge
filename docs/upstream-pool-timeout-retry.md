# 浏览器上游 HTTP 错误重试

## 现场依据与范围

2026-11-08 手工 Codex 测试中，前 10 条请求成功，一条长流持续约 681 秒后正常完成。16:59:23 发起的下一条请求在约 15ms 内分配到本地标签 `kpool=4`，约 47.5 秒后收到 NVIDIA HTTP 500：

```text
Pool#acquire(Duration) has been pending for more than the configured timeout of 45000ms
```

失败请求尚未产生 thinking、正文或工具调用。45 秒来自 NVIDIA 上游的内部连接池限制，增加桥接总时限或心跳频率不能改变它。错误本身无法确定上游耗尽连接的具体原因，也不能证明本地五标签并发是根因。

2026-11-09 的 CC 实网测试还遇到了明确 HTTP 500、但错误正文没有在有界读取窗口内返回的情况。CC 随后以相同历史改用非流式请求。新增明确 HTTP 500/502/503/504 的一次重试，使这类失败也有机会在原 SSE 连接中恢复。

重试在 browser 模式的共享事件源中处理，覆盖 Anthropic Messages 与 OpenAI Responses 的流式和非流式接口。OpenAI/NVCF 直连模式不受此策略影响。

## 重试规则

- 同时具备真实 HTTP 状态 500 和上述连接池超时特征时，使用专项策略：默认最多额外尝试 2 次，首次等待 5–6 秒，第二次等待 10–11 秒。
- 其它明确收到的 HTTP 500/502/503/504 使用独立策略：默认额外尝试 3 次，依次等待 5–6、10–11、20–21 秒。覆盖 `Retries exhausted: 3/3`；其中 `3/3` 是上游自己的重试计数，与桥接次数无关。错误正文为空或读取不完整时仍保留真实 HTTP 状态。专项连接池策略优先；其次数耗尽后不会再借用通用重试预算。
- 基础退避按指数翻倍、上限 30 秒，另外加入至多 1 秒随机延迟。HTTP 429、501 等其它状态不自动重试；错误文本中的状态码不能替代实际收到的 HTTP 状态。fetch 建立失败仍使用独立的 1 次、2–2.4 秒策略。
- HTTP 200 中结构化 SSE 错误码 500/502/503/504、明确的网络读流故障、首数据/空闲超时、缺少完成标记的 EOF 使用新的独立流错误策略：默认额外尝试 2 次，等待 5–6、10–11 秒。SSE code 和网络故障分别记录，不能冒充 HTTP 状态。取消、参数 JSON 错误、缓冲超限、未知错误不重试。
- Messages 默认实时交付开头的 thinking，暂存正文和工具，确认整条上游响应成功且参数合法后才交付。失败轮次已显示的 thinking 保留，正文与工具全部丢弃，允许在原 SSE 连接重试；非流式丢弃失败轮次的全部内容。`BROWSER_MESSAGES_DEFER_OUTPUT=0` 及 Responses 维持原交付保护：任何已交付 thinking、正文或工具都阻止重放。详见 [CC 中途响应恢复](cc-midresponse-recovery.md)。
- 重试使用同一请求体；不修改 effort、预算、历史、工具或采样参数。原有空回答/占位文本纠正仍有独立的一次机会，各错误重试不会消耗或重置它。不同类型错误及占位纠正连续出现时，默认最多 10 次上游尝试；相同类型连续失败则受自己的次数上限约束。
- 所有尝试、排队、页面准备和退避共用原始 `BROWSER_TIMEOUT`，默认 3600 秒。剩余时间不足以完成完整退避时，立即返回原始上游错误；总预算已到时不再打开上游流。

## 连接、清理与取消

失败尝试先关闭事件源并执行浏览器流清理，然后才开始等待。失败标签沿用池内现有隔离与恢复流程，重试重新从健康标签中借用。退避期间不持有标签，使用异步等待，不阻塞服务中的其它 CLI。

下游保持同一条 HTTP/SSE 连接。Responses 保留同一个 response ID 和事件序号序列，不暴露中间失败或重复发送 `response.created`；Anthropic 不重复发送 `message_start`。退避开始时及等待期间按 `BROWSER_HEARTBEAT_SEC` 发心跳，设置为 0 时关闭。客户端断开或任务取消会中断等待，禁止继续尝试。

达到重试上限时保留原始错误。Responses 发一个 `response.failed`，Anthropic 发一个 SSE `error`，都不伪造成功结束；非流式接口沿用既有 HTTP 错误返回。该策略缓解间歇性错误，无法保证上游持续拥堵时成功。

页面补丁版本 4 修复了错误正文读取期间的取消竞争：页面前端可能在收到 HTTP 400/500 响应头后立即取消原始信号，导致桥接的克隆流只剩 `AbortError`。现在收到错误响应头后解除前端信号传递，让桥接在原有 5 秒、8192 字符上限内收集正文；客户端取消和总时限仍通过桥接自己的控制器中止读取，成功响应继续传递前端取消。真实 HTTP 状态保持原样，读取正文不会把 HTTP 400 变成可重试的 5xx。

2026-11-11 的独立本地 CDP 探针先在 400、500 两种场景复现正文丢失，再验证两种正文完整读取、成功流前端取消和错误正文期间客户端取消，共四项通过；280 项完整回归通过。可运行 `PYTHONPATH=. python3 tests/probe_browser_http_abort_body.py --cdp-port 9225` 复查，它只访问自己的本地页面和标签。现场已丢失的上游正文无法恢复，诊断与部署证据见 [错误正文取消修复](evidence/cc-bridge-http-error-body-abort-2026-11-11.json)。

## 配置与日志

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `BROWSER_POOL_TIMEOUT_RETRIES` | `2` | 额外尝试次数；0 关闭 |
| `BROWSER_POOL_TIMEOUT_BACKOFF` | `5` | 初始退避秒数，按指数增长并加入随机延迟 |
| `BROWSER_HTTP_5XX_RETRIES` | `3` | 明确 HTTP 500/502/503/504 的额外尝试次数；0 关闭 |
| `BROWSER_HTTP_5XX_BACKOFF` | `5` | 通用 HTTP 5xx 初始退避秒数 |
| `BROWSER_STREAM_RETRIES` | `2` | 明确 SSE 临时错误及读流故障的额外尝试次数 |
| `BROWSER_STREAM_BACKOFF` | `5` | 流错误初始退避秒数 |
| `BROWSER_MESSAGES_DEFER_OUTPUT` | `1` | 实时思考，正文与工具验证成功后交付；0 恢复立即交付 |

现有启动脚本无需增加参数，读取模块默认值及环境变量即可。这些配置和代码在下次正常启动时生效，不会动态改变运行中的进程。

`browser_start` 继续使用稳定的请求 ID 和递增的 `attempt`。`upstream_retry` 记录原因、重试次数、下一次 attempt、退避秒数、剩余总时间、原始错误以及本次 usage/内容计数。`upstream_retry_skipped` 记录 `content_committed`、`retry_limit` 或 `deadline`。最后失败仍记录 `browser_error`，成功仍记录 `browser_done`。日志不新增提示词或工具参数。
